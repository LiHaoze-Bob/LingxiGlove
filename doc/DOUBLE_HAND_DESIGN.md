## 1. 目标与非目标

### 1.1 目标（Goals）
1. **语义层目标**：将"相对运动学信息 ≠ 两只手独立识别结果之和"这一事实，显式建模到系统架构里，使得双手协同手势（如"朋友/冲突/帮助/比较"）在识别层可分。
2. **工程层目标**：在 **2 片 ESP32-S3（Nano ESP32 或 DevKit）** 的资源预算内完成双手采样、时钟对齐、双流推理。
   - 采样帧率 20 Hz（与 MVP `config.h` 的 `SENSOR_READ_INTERVAL = 50` ms 一致），**单帧处理必须 ≤ 50 ms** 才能不丢帧
   - 端到端时延（含云端往返，对需要云端的指令而言）目标 ≤ 500 ms（人对语音反馈的无卡顿感知阈值）
   - 上述两个预算**同时成立**：前者保证识别流水线不堆积，后者保证用户体验
3. **验证层目标**：每一项物理量（对齐误差、测距精度、识别 F1）都要有**可复现的实测脚本 + 数值区间**，而非口号。

### 1.2 非目标（Non-Goals）
- **不追求**连续句子的自由手语翻译。本白皮书只覆盖**孤立手势词 + 端云分级调用**。长句子由云端 Sign-Transformer 处理，属 P5 阶段 out-of-scope。
- **不追求**亚毫米级距离精度。D1 已诚实披露亚样本插值在 chirp 输入下有 ~1 样本本质偏置（见 §4.3），本版本**精度下限锁定 c/fs ≈ 7.15 mm**。
- **不覆盖** UWB、Vision、Leap Motion 等方案。这些方案在 SOLUTION_REVIEW §2.3 的候选表里已作对比，本白皮书只沿着"零增量硬件 + 声学 TDOA"这一条工程主线展开。

**角色分工（完整方案）**：
- **Master（右手）**：采样 + 推理 + 云端交互 + TTS 播报；挂 MAX98357A + 喇叭 +（待补）INMP441 麦
- **Slave（左手）**：采样 + 通过 ESP-NOW 上传 HandFrame；挂 MAX98357A + 喇叭 +（待补）INMP441 麦

"一主一从"拓扑有两个决策动因：
1. MVP 代码已经把 WiFi/HTTP/LLM/TTS 全部跑在右手主控上，新增 Slave 不触碰主链路
2. 右利手的主动作在右手，Master 承载语义推理更自然，左手仅做辅助特征

**测距链路选型（避免读者误读为单向架构）**：
- **本白皮书 v0.1 的最终设计目标**：**双向 RTT-TOF**。双方都具备发/收能力，
  一轮测距包含"Master 发 → Slave 收"和"Slave 发 → Master 收"两条路径，
  取两条 TOF 的**差分** `(t_MS − t_SM)/2` 可完全抵消跨板时钟偏差和固定收发延迟，
  这是物理上最稳健的相对距离观测。
- **当前 D1 仿真 / D2 POC 为简化起点**：只验证"一方发 / 另一方收"的**单向链路**，
  以独立验证 chirp 生成、定点相关器、CFAR 判据这三个原子能力。单向链路
  **无法给出绝对距离**（缺跨板同步），POC 只用作相对位移观测。
- **从单向 POC 到双向 RTT 的工程跨越**需要先补齐 INMP441 麦克风和跨板 GPIO 硬触发线，
  见 §7 D4 阶段。

## 3. Layer 1：时钟同步

### 3.1 问题陈述
两块 ESP32-S3 用各自的 240 MHz 晶振独立计时，`millis()` 最初并不在同一时钟域。20 Hz 采样下单帧窗 50 ms，要求跨板对齐误差 ≤ 5 ms（10% 帧窗），否则双手同帧的语义会错位。

### 3.2 设计：ESP-NOW + Master 打戳 + Slave EWMA

**数据面**：Slave 每 50 ms 采一帧，立刻 `SendHandFrame()` 推给 Master（`HandFrame` 结构见 §3.4）。Slave 在包里**不自行打时间戳**，只带单调自增 `seq_no`。

**时钟面**：Master 收到 HandFrame 的瞬间用**本机 `millis()`** 回填 `master_timestamp_ms`，再写入环形缓冲。这样"Master 时钟域"成为系统唯一基准，不需要跨板时钟校正。

**对齐**：Master 自采样一帧 `right_frame(t_r)` 时，在 Slave 环形缓冲里二分查找 `seq_no` 距离当前最近、且时间偏移 < 25 ms 的 `left_frame`，配对输出 `(left, right, Δt)`。

### 3.3 为什么选 ESP-NOW 而不是 WiFi UDP
- ESP-NOW **链路层直连**，不过 AP；Espressif 官方文档将其定位为"低延迟、适合实时控制"，
  但未公开给出具体的 P99 延迟数字（不同信道占用/距离/发射功率差异很大）。**本白皮书
  不引用任何虚构的"< 数 ms"断言**，真实延迟分布留 P2 双板实测后填入。
- ESP-NOW **无握手开销**，`send_cb` 能直接报告物理层 ACK 成败，方便丢包统计（当前
  `esp_now_sync.cpp` 的 `GetEspNowTxCount()` / `GetEspNowTxFailCount()` 已提供这个能力）
- 与 WiFi STA 共频，无需在双模式间切换（代码 `esp_now_sync.cpp` 已实现 STA + ESP-NOW 共存）

### 3.4 接口（A1 阶段已落地）
位置：`src/LingxiGlove_Main/esp_now_sync.h`

```cpp
struct __attribute__((packed)) HandFrame {
    uint32_t master_timestamp_ms;   // Master 侧回填；Slave 发送时为 0
    uint16_t seq_no;                // Slave 单调递增，循环至 65535
    uint16_t reserved0;             // 预留对齐位（当前恒 0）
    int16_t  ax, ay, az;            // IMU 原始 LSB，±2g full-scale
    int16_t  gx, gy, gz;            // IMU 原始 LSB，±250°/s
    uint16_t flex[5];               // Flex ADC 原始 0..4095
};
// sizeof(HandFrame) == 30 bytes （本机 clang++ -std=c++11 实测）
// offsets: ts@0  seq@4  rsv@6  ax@8  flex@20  end@30
// ESP-NOW 单包上限 250B，余量 220B 充足

bool InitEspNowSync(EspNowRole role, const uint8_t peer_mac[6]);
bool SendHandFrame(const HandFrame& frame);
void RegisterHandFrameHandler(HandFrameHandler handler);
```

**编译开关**：`ENABLE_ESPNOW_SYNC=0` 时整套代码零成本被剔除，MVP 单手行为不受影响。

## 4. Layer 2：感知 — 声学 TDOA 相对距离

### 4.1 问题陈述
IMU 只给加速度 + 角速度，二次积分得位置会在秒级别漂出米级误差，不能支撑"朋友（双手食指互勾，距离 ≈ 2 cm）"这类语义。需要**独立的相对距离观测量**。

### 4.2 方案：17–19 kHz chirp + 匹配滤波
- **信号**：5 ms 的 17–19 kHz 线性 chirp（加 Hann 窗抑制起止突变），归一化到 int16 峰值 28000
- **每一方的硬件**：MAX98357A + 喇叭（发）+ INMP441 I2S 麦（收），48 kHz 采样
- **接收侧算法**：在 30 ms 滑动窗口上做 int16×int16→int64 **朴素滑动相关**
- **距离推导**：相关 argmax 的样本号 `k*` → 飞行时间 `k*/fs` → 距离 `c × k*/fs`
- **精度下限**：`c/fs = 343/48000 ≈ 7.15 mm`（单样本量化地板，SNR → ∞ 也消不掉）

**发射节奏（设计目标 vs POC 现状必须分清）**：
| 时序口径 | 频率 | 说明 | 状态 |
|---|---|---|---|
| **白皮书 v0.1 设计目标** | 20 Hz（每 50 ms 一次） | 与 IMU/Flex 采样同频，识别层每一帧都有同期距离观测 | 设计层目标 |
| **D2 POC 当前实现** | 2 Hz（每 500 ms 一次） | `kTxIntervalMs = 500u`，POC 只验证发-收闭环，不追时序预算 | 已落地 |

从 500 ms → 50 ms 的工程改造需要三件事：① MAX98357A 连续喂 I2S 的缓冲编排、
② 相关器预算 ≤ 50 ms 窗口（目前 <3 ms，有 15× 余量）、③ 相邻 chirp 间最小静默时长
以避免多径残响。关于第 ③ 点——**17–19 kHz 的空气吸收不是主要制约**：按 ISO 9613-1
在 20 °C / 50 %RH 条件下，18 kHz 的空气吸收系数 α ≈ **0.4 dB/m** 量级（远小于早期
草稿误写的"6 dB/m"），因此 1.5 m 量程下直射波只衰减 <1 dB，可忽略；真正需要处理
的是室内**墙面/桌面多径回波**导致的伪相关峰，30 ms 采集窗 + CFAR 判据（见 §4.5）
已经压制了这一项。此时序优化 + 多径实证留在 **D3/D4 阶段**推进。

### 4.3 D1 实测数据：Python 仿真（500 次 Monte Carlo / 格子）
完整表格见 `doc/acoustic_tdoa_simulation_results.md`，下表节选代表性距离（0.1 / 0.5 / 1.0 / 1.5 m）：

| 真实距离 D | SNR=30 dB | SNR=20 dB | SNR=10 dB | SNR=0 dB | SNR=-10 dB |
|---|---|---|---|---|---|
| 0.10 m | 0.04 mm | 0.04 mm | 0.04 mm | 13.7 mm | 905 mm ⚠️ |
| 0.50 m | **0.21 mm** | **0.21 mm** | **0.21 mm** | 12.6 mm | 797 mm ⚠️ |
| 1.00 m | 0.42 mm | 0.42 mm | 0.42 mm | 13.1 mm | 740 mm ⚠️ |
| 1.50 m | 0.63 mm | 0.63 mm | 0.63 mm | 13.8 mm | 736 mm ⚠️ |

**读数口径**（与 SOLUTION_REVIEW §2.3 第 2 层一致）：
- SNR ≥ 10 dB：精度被距离量化残差 `round(D·fs/c)·c/fs − D` 决定，与 SNR 解耦
- SNR = 0 dB：RMSE ≈ 13 mm（约 2 个采样点），**仍满足 ±5 cm 工程指标**
- SNR = -10 dB：匹配滤波峰被噪声吸走，**物理不可用**

### 4.4 亚毫米精度路径（诚实披露：已放弃）
早期版本实现过"频域分数延迟 + 三点抛物线亚样本插值"，希望把精度压到亚毫米。经 5 轮诊断发现：
- 抛物线插值对 **δ 冲激**只有 ~0.1 样本残差（理论符合）
- 但对 **chirp 匹配滤波输出**，chirp 自相关主瓣非对称（线性调频的相位-时间耦合），抛物线拟合有 **~1 样本本质偏置**，比理论预期差一个数量级
- 用 16× 过采样的"真·延迟 0.25 样本 chirp"回归，抛物线估计偏置仍 +0.508 样本

结论：**本白皮书 v0.1 接受 7 mm 量化地板**，D3 真机实测阶段再评估是否引入 sinc 插值 / 复相关相位法 / 提高采样率。

### 4.5 D2 Arduino POC 现状
位置：`src/tests/test_acoustic_tdoa/`，单 sketch 通过 `#define ROLE_TX/ROLE_RX` 切换角色。

**已落地特性**：
- 参数与 D1 完全一致（48 kHz / 5 ms / 17–19 kHz / Hann / peak=28000）
- **定点相关**：int16×int16→int64 朴素滑动相关，单次 <3 ms @ 240 MHz，不依赖 FFT / 浮点栈
- **CFAR 检测判据**：主峰必须 ≥ 4× 于保护带外次峰，不依赖能量绝对值（避免早期版本用"经验阈值 20M"这种假设实现）
- **相对位移输出**：打印 `window_offset_samples` + 相邻两次差值 `rel_delta_mm`

**诚实披露的 POC 限制**（B1 不打补丁，留 D3 解决）：
- 当前 POC **无跨板硬同步**，RX 算到的 argmax 只是"chirp 在 30 ms 采集窗里的位置"，**不等于 TX→RX 绝对飞行时间**
- 因此 POC 只能输出**相对位移**（双手间距的相对变化），不能直接给绝对距离
- 要得到绝对距离，必须在 D3 阶段把 `esp_now_sync.h` 或一条 GPIO 同步线接进来，让 RX 知道 "TX 发出 chirp 的那一刻对应 RX 本地时钟 t=0"

### 4.6 同步抖动对绝对距离的物理限制
**关键物理事实**（声速 × 时间即距离，无规避空间）：
- 同步抖动 Δt → 距离误差 Δd = c · Δt，每 1 ms → 343 mm
- 这是 §2.1 验证层目标里"测距 ≤ 5 cm"的**上游硬约束**：允许的同步抖动 ≤ 5cm/343 m/s ≈ **146 μs**

三档同步方案的数量级对比：

| 同步方式 | 典型时间不确定度 | 对应距离误差 | 是否够用（5 cm 指标） |
|---|---|---|---|
| 裸 ESP-NOW 用 `millis()` 对齐 | 1–3 ms（毫秒级 OS 调度 + 无线排队抖动；Espressif 文档定性为"毫秒级" ） | 343–1029 mm | ❌ 差一个数量级 |
| ESP-NOW + RX 侧 `micros()` + 固定偏移校正 | 数百 μs（去掉 OS 调度抖动，仅剩无线层） | ~100–300 mm | ❌ 仍差 2-6× |
| **一条跨板 GPIO 硬触发线 + ISR 打戳** | ESP32 GPIO ISR 典型 μs 级响应（ESP-IDF `gpio_install_isr_service` 文档描述为"极低延迟"，具体 ISR-to-handler 延迟跟并发负载有关） | **μs 级 × 343 m/s ≈ 亚毫米** | ✅ 远超指标 |

> 上表"μs 级"保留**模糊量级**描述而非具体数字，是因为 GPIO ISR 响应时间在
> FreeRTOS 下受中断优先级、是否持有锁、缓存命中等多重影响，简单地写"< 20 μs"
> 会误导读者。真实数字要在 D3 阶段用**双板同一信号对打 GPIO + 逻辑分析仪**
> 测量，预期量级是 μs 级、远低于 146 μs 上限。

**结论**：**纯 ESP-NOW 同步不足以支撑绝对距离测量**，D3 必须配一条跨板 GPIO 硬触发线
（Master 发 chirp 前拉高 GPIO，Slave 用边沿触发 ISR 记 `esp_timer_get_time()`）。
硬件团队在 P2 阶段布板前需预留 1 条跨板 GPIO。

## 5. Layer 3：识别 — 双流 1D-CNN

### 5.1 输入张量
每一次推理的输入是**时间对齐后**的双手窗口，时长 1 秒（20 帧）：

```
shape = (T=20, C_total=23)
 ├── 左手 IMU6  (T, 6)      ax/ay/az/gx/gy/gz
 ├── 左手 Flex5 (T, 5)
 ├── 右手 IMU6  (T, 6)
 ├── 右手 Flex5 (T, 5)
 └── 相对距离  (T, 1)       来自 Layer 2 声学 TDOA，未知时填 -1
```

### 5.2 网络拓扑（与 SOLUTION_REVIEW §2.3 第 3 层一致）

```python
left_in  = Input((20, 11))   # IMU6 + Flex5
right_in = Input((20, 11))
dist_in  = Input((20, 1))

# 主干
left_f  = Conv1D(32, 3) → Conv1D(64, 3) → GAP    # (64,)
right_f = Conv1D(32, 3) → Conv1D(64, 3) → GAP    # (64,)

# 显式协同特征
cross = Concat([
    abs(left_in - right_in),      # 对称性
    left_in * right_in,           # 协同性
    dist_in                        # 相对距离（声学来源）
])
cross_f = Conv1D(16, 3) → Conv1D(32, 3) → GAP   # (32,)

logits = Dense(N_classes, softmax)(Concat([left_f, right_f, cross_f]))
```

**设计动因**：
- 双流而非单流 concat：保留单手语义通路，便于做"左/右手独立 F1"监控
- Cross-stream 用**手工先验**（差、积、距离）而非纯学习：参考 ST-GCN / MS-G3D 的经验，在数据量有限时（竞赛场景单人打每类 50 次 = 2500 样本）手工特征更稳
- 距离通道单独喂给 cross 而非拼到单手 Flex：距离是"两手的属性"而非"某只手的属性"，拓扑上更干净

### 5.3 推理预算（目前是**规划预估**，非实测）

**重要前置**：截至 B1 成文时，`src/LingxiGlove_Main/gesture_recognizer.cpp` 里真正
落地的是 `RuleBasedRecognizer`（规则识别器），**还没有任何训练过的 CNN 跑在端侧**。
因此下表所有数字都是"规划依据"，不是"已实测"。

| 子模块 | 参数量 | 推理延迟 | 依据 |
|---|---|---|---|
| 单手 1D-CNN（INT8 量化） | ~12 K | ~15 ms | `doc/Edge_Impulse_ESP32_S3_训练指南.md` §7.1 给出的 Edge Impulse 官方 INT8 对照表典型值（FP32 → INT8 的 ~40% 加速是 EI 官方公开数据，具体绝对值要看模型结构，P1 训练后以 Model performance 页实测为准） |
| 双流 + cross 融合版 | ~30 K | ~40 ms | 保守估计：双流两条骨干 + 一条 cross 骨干 ≈ 3× 单手计算量。真机实测留 P4 填入 |
| TDOA 相关器 | n/a | ~3 ms（估算） | 288k MAC / 240 MHz ≈ 1.2 ms 纯 ALU，考虑流水线停顿和 I2S 搬运取 2-3× 余量。真机实测留 D3 填入 |
| 同步对齐（环形缓冲最近邻） | n/a | <1 ms | O(log N) 二分，N ≤ 100（约 5 秒历史帧） |

**端到端上界** ≈ 40 + 3 + 1 = **44 ms < 50 ms 帧窗**，数量级有余。
但**任一真实测量出来显著偏离这个预估 2×以上，都应当触发架构回炉**——
比如双流推理真机实测 90 ms，就必须转向模型剪枝 / 双核分工 / 降帧率，
而不是假装还能继续。

### 5.4 训练数据策略（规划 · 当前数据集 = 0 样本）

**前置声明**：B1 成文时仓库内**没有任何采集到的训练数据**，也没有 CNN 权重。
以下策略是 P1/P4 阶段的规划，不是"已经这么做了"。

- 每类每人采 50 次，左右手各打一次 → 样本量 = 类数 × 人数 × 100
- **水平翻转增强**：左手样本可通过镜像生成"虚拟右手样本"，等价于免费 ×1.5 数据量
- **时间抖动增强**：± 2 帧随机平移，覆盖手势起止时刻不准的噪声
- 评估：分别算 `F1_left / F1_right / F1_bimanual`，任一低于整体 5 个百分点则回炉
- 采集执行路径：走 MVP 已落地的"采集模式"串口命令（见 `src/LingxiGlove_Main/README.md` 的
  `c` 命令，打 CSV 到 Serial），再用 `tools/` 下的脚本转 Edge Impulse 数据集格式（脚本 P1 再写）

### 7.2 关键路径与"一票否决"节点

```
已完成: A1 (同步接口) ──┐
                        │
已完成: D1 (仿真) ───D2 (单向 POC) ───┐
                                      │
                                      ▼
                D3 (真机 chirp 收发 + GPIO 硬同步)   ← go/no-go #1
                                      │
                                      ▼
                D4 (双向 RTT-TOF，抵消时钟偏差)       ← go/no-go #2
                                      │
                                      ▼
                P2 (双板实测) ── P4 (双流 CNN) ── P5 (云端)
```

**D3 是第一个一票否决节点**：如果真机实测下，引入一条跨板 GPIO 硬同步后
（见 §4.6），单向链路的绝对距离 RMSE 仍明显大于 15 mm，则说明 MAX98357A 喇叭
在 17–19 kHz 的响应或 INMP441 的模拟前端引入了无法忽略的色散/群延迟，
此时要么切换器件、要么放弃 TDOA、改投 UWB（SOLUTION_REVIEW §2.3 候选 A）。

**D4 是第二个一票否决节点**：双向 RTT-TOF 依赖"两方几乎同时各发一次 chirp
且互不干扰"的调度，如果 D4 实测双向信号互扰严重（由于两只手套在空间上
相距仅 10 cm–1.5 m，同频 chirp 可能重叠），就要引入 TDM（时分复用）或双频
（例如一方 17–18 kHz、另一方 18–19 kHz）分离。TDM 会把每次有效测量的
延迟翻倍，双频则要生成两份模板。哪一种更优要靠 D4 实测才能判断。

这两个决策点**白皮书显式写出是为了让项目有明确的 go/no-go 预案**，
而不是等答辩前被问到"如果你们真机做不出来怎么办"才临场应对。

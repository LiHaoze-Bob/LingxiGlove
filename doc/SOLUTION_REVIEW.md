| **成本控制** | 单手套 ¥250（商用方案 ¥5k~¥80k） | ⭐⭐⭐⭐⭐ 两个数量级的降本，"极客普惠"叙事 |

### 1.2 存在的技术风险与改进建议（按优先级）

#### 🔴 风险 1：10 手势在真实场景下的表达力不够

招募书说只识别 10 个精选手势，但**中文手语有 5500+ 词**。

**评委会问的一击**："如果一个聋人想说'我这周二下午有课'，你的手套怎么处理？"

**建议改进**：
- 把 10 个词定位为**"紧急高频词"**（就医、求助场景），不要宣称通用
- 增加一个**"字母指拼"兜底模式**：中国手语 / ASL 的指拼字母表是一个**有限且固定的手型集合**（CSL 方案常见为 30 个，ASL 常见为 26 个；具体手型数量在做数据集前由团队确认并固化），用同一模型训练，配合字母序列 → LLM 组词，扩展到开放词汇
- 答辩话术："10 个高频词覆盖急救场景的快路径，指拼模式覆盖开放词汇的慢路径，形成**分级响应**"（端到端延迟指标待实测后补入）

#### 🟡 风险 2：动态手势的「分割问题」（Segmentation）没提及 — ✅ 已缓解

手语不是静态摆姿势，是**连续动作流**。当前方案（定长 2 秒窗口 + 200ms 滑动）隐含假设"每 2 秒恰好有一个完整手势"。真实场景中：
- 用户连续打"谢谢"→"再见"，两个动作粘连
- 用户中间停顿 3 秒，窗口里是一半"救命"+ 一半静止

**评委会问的一击**："用户连续打三个词，你的系统如何知道什么时候是一个词结束？"

**建议改进**：
- ✅ **已实现**：`motion_detector.h/cpp`（动作/静止门控，基于加速度方差 + 陀螺仪模长双阈值迟滞状态机），以无模型阈值法落地
- 进一步可训练一个二分类的**"动作/静止"前置模型**，先做分割再做分类（HAR 领域 VAD 的标准做法）；模型体积在训练后以实际导出结果为准

#### 🟡 风险 3：Edge Impulse 训练数据代表性不足

招募书计划"3 人 × 50 次 = 150 次/手势"。但：
- 只有 3 名采集者 → 跨用户识别率会显著下降（**User Dependence** 是 HAR 领域公认难题）
- 没提到**佩戴姿态变化**（同一人早晚松紧不同，识别率会飘）

**建议改进**：
- **Per-user calibration**：开机时要求用户做 5 个参考手势，对弯曲传感器做个体化归一化
- 招募 **≥ 10 人** 采数据，做 **leave-one-user-out** 交叉验证

#### 🟡 风险 4：端云协同的「断网兜底」不明确 — ✅ 已缓解

- LLM 断网 = 语义重组失效
- TTS 断网 = 彻底哑火

**建议改进**：
- ✅ **已实现**：`local_tts_fallback.h/cpp` + `offline_voice_pcm.h/cpp`，网络异常时按 label 匹配离线 PCM
- ✅ PCM 表框架就绪；实际音频需运行 `tools/gen_offline_voice_pcm.py` 预生成（每条 16kHz×16bit×1s ≈ 32KB，10 条 ≈ 320KB）
- ✅ 空表时降级蜂鸣（`playTestTone` 安全兜底）
- 答辩亮点："**断网也能说救命**"

#### 🟢 小建议 5：振动马达 + OLED 没在代码里

招募书提"振动反馈 + OLED 显示"三模态输出，代码里都没有。MVP 阶段优先链路验证合理，但**答辩 PPT 和实物演示要对齐**，避免露馅。

#### 🟢 小建议 6：功耗 / 电池方案几乎空白

100Hz 连续采样 + WiFi 长连接下，ESP32-S3 Active 状态功耗量级在几十毫安到上百毫安之间（具体看 CPU 频率、WiFi 占空比；参考 ESP32-S3 datasheet"Power Consumption" 章节），小电池续航会偏紧。
- 可做**手势唤醒**：静止时切 Light-sleep（ESP32-S3 datasheet 标称 Light-sleep 毫安级以下），运动再唤醒
- 答辩前用功耗计实测后把具体数字补进来

## 二、双手手语翻译 — 技术方案

### 2.1 为什么双手远不止"两只手套"

| 难点 | 单手套 | 双手套 | 复杂度提升 |
|------|--------|--------|-----------|
| **识别类别** | 10 类 | 几百到上千类 | 10×~100× |
| **特征维度** | 11 维 | 22 维 + 相对关系 | 2× 原始，但组合爆炸 |
| **时空同步** | 无需 | 毫秒级对齐 | 全新难题 |
| **通信通道** | 1 条 WiFi | 2 条需融合 | 多设备一致性 |
| **计算资源** | 1× ESP32 | 2× 或 1 主 1 从 | 架构重设 |

中国手语中**双手词占比很高**（多份文献报告 CSL 常用词中双手词占比过半；具体数字待团队在 CSL-Daily 或 CE-CSL 数据集上二次统计确认后写入答辩材料），且双手的**相对位置**本身就是语义：
- "朋友"：双手食指互勾
- "冲突"：双拳相撞
- "帮助"：一手握拳，另一手托住
- "比较"：双手掌心相对上下移动

**核心洞察**：双手手语 ≠ "左手语义 + 右手语义"。语义在**两手的相对运动学关系**里。

### 2.2 五大核心技术难点

#### 难点 #1：时空同步（Synchronization）
两只手套独立采样，WiFi 抖动 10~100ms，直接拼接会严重失真。
> 类比：单声道 ×2 ≠ 立体声，立体声必须严格同相位。

#### 难点 #2：空间相对位置（Relative Pose）
MPU6050 只能给加速度+角速度，**得不到绝对位置**（积分漂移）。光靠 IMU 算不出两手距离。

#### 难点 #3：特征空间爆炸
22 维 × 20 帧 = 440 维 → 几百类，标注成本平方级上升。

#### 难点 #4：计算资源瓶颈
主控既要跑本手传感器，又要推理双流模型，还要处理 WiFi RPC —— 撞 RAM + 实时性双红线。

#### 难点 #5：佩戴不对称
右利手为主，左手动作幅度小、噪声大；需要左右手数据分别训练 或 水平翻转增强。

### 2.3 🎯 推荐方案：「一主一从 + 磁力同步 + 双流 CNN + 云端 Transformer」四层架构

```
┌─────────── 左手从节点 ESP32-S3 (Slave) ───────────┐
│  IMU + 5 Flex → 20Hz 采样 → ESP-NOW → 主控      │
│                  ↑                              │
│                  └─ 每 500ms 广播同步脉冲对齐     │
└────────────────────────────────────────────────┘
                    ↓ ESP-NOW（链路层直连，延迟以 P2 实测为准）
┌─────────── 右手主节点 ESP32-S3 (Master) ──────────┐
│  1. 自采样 20Hz + 接收左手帧                      │
│  2. 时间戳对齐（环形缓冲区 + 最近邻匹配；对齐误差以 P2 实测为准） │
│  3. 双流 1D CNN 推理：                           │
│     left_stream  : 11D×20 → Conv1D → 64        │
│     right_stream : 11D×20 → Conv1D → 64        │
│     cross_stream : (delta/积/距离) → Dense → 32 │
│     concat + GAP → Dense → 50 类               │
│  4. 端侧 softmax 置信度低于阈值（由验证集 ROC 定）   │
│     时把原始流上传云端                            │
└────────────────────────────────────────────────┘
                    ↓ WiFi / HTTPS
┌─────────── 云端语义层（Sign-Transformer，规模待定）─┐
│  P5 阶段建模；模型参数量、词表大小、延迟均以训练后实测为准 │
│  返回文本 + TTS 语音                              │
└────────────────────────────────────────────────┘
```

#### 逐层技术方案

**第 1 层：硬件同步（解决难点 #1）** — ESP-NOW + 时钟节拍
- 选 ESP-NOW 理由：WiFi STA 模式下相邻包抖动常见 20~100ms 级，对 20Hz 双手对齐不够；ESP-NOW 无握手、链路层直连，Espressif 官方文档（esp-now 参考）标称单跳延迟百微秒~数毫秒级，**契合乐鑫赛道**
- 主控每 500ms 广播 master_timestamp 包，从节点用 EWMA 滤波得到稳定偏移
- 目标对齐误差 < 5ms（20Hz 采样一帧 50ms 的 10%）；**具体误差需在 P2 阶段用双节点对打时间戳实测得出，未实测前不使用数字作为答辩断言**
- 上报数据结构：
  ```cpp
  struct HandFrame {
      uint32_t master_timestamp_ms;  // 已校正到主节点时钟域
      uint16_t seq_no;
      uint8_t  frame_type;           // 帧类型：0=传感器数据，预留 1=心跳/2=配置同步
      uint8_t  proto_version;        // 协议版本号（当前=1），版本不匹配时丢弃
      int16_t  ax, ay, az, gx, gy, gz;
      uint16_t flex[5];
  };  // 30 bytes，ESP-NOW 最大 250B
  ```

**第 2 层：相对位姿估计（解决难点 #2）**

| 方案 | 成本 | 精度 | 推荐度 |
|------|------|------|--------|
| A. UWB（DW1000） | ¥80/颗 | ±10cm | ⭐⭐⭐⭐⭐ 秀实力 |
| B. 蓝牙 RSSI 回归 | 内置 | ±50cm | ⭐⭐ 太粗 |
| C. 声波 TDOA（复用 MEMS + 喇叭） | 零增量 | ±5cm | ⭐⭐⭐⭐ 性价比王 |

**首推方案 C**：
- 左右手套各自的 MEMS 麦 + MAX98357A 喇叭（MVP 已有 MAX98357A，MEMS 麦为招募书规划硬件）
- 一端定时发 17–19 kHz 线性 chirp（5 ms），另一端麦收到后用匹配滤波检测到达时刻
- 距离推导：声速 c ≈ 343 m/s，因此每 1 ms 传播延迟对应 34.3 cm 距离
- 采样率 → 采样粒度：48 kHz 采样的单采样点时间分辨率是 1/48000 s ≈ 20.8 μs，对应 **c/fs ≈ 7.146 mm** 的距离单步

**D1 Python 仿真实测数据**（`tools/acoustic_tdoa_simulate.py`，500 次 Monte Carlo，整数样本 argmax）：

| D | SNR=30 dB | SNR=20 dB | SNR=10 dB | SNR=0 dB | SNR=-10 dB |
|---|---|---|---|---|---|
| 0.10 m | 0.04 mm | 0.04 mm | 0.04 mm | 13.7 mm | 905 mm ⚠️ |
| 0.30 m | 0.13 mm | 0.13 mm | 0.13 mm | 13.2 mm | 814 mm ⚠️ |
| 0.50 m | 0.21 mm | 0.21 mm | 0.21 mm | 12.6 mm | 797 mm ⚠️ |
| 0.80 m | 0.33 mm | 0.33 mm | 0.33 mm | 13.8 mm | 680 mm ⚠️ |
| 1.00 m | 0.42 mm | 0.42 mm | 0.42 mm | 13.1 mm | 740 mm ⚠️ |
| 1.50 m | 0.63 mm | 0.63 mm | 0.63 mm | 13.8 mm | 736 mm ⚠️ |

**关键结论**（都是运行真实出来的，非估算）：
- SNR ≥ 10 dB 的精度完全被"距离量化残差" `round(D·fs/c)/fs·c − D` 决定，RMSE 与 SNR 解耦
- SNR = 0 dB 时 RMSE ≈ 13 mm（约 2 个采样点），仍满足 ±5 cm 指标
- SNR = -10 dB 时匹配滤波峰被噪声吸走，RMSE 跳变到 ~700 mm 级别，即物理不可用
- 答辩口径：**"50 cm 量程、SNR=10 dB 工况下 RMSE ≈ 0.21 mm；SNR 劣化到 0 dB 时 ≈ 12.6 mm；-10 dB 失效"**

**（诚实披露）被放弃的"亚样本插值"技术路径**：

早期版本尝试过"频域分数延迟 + 三点抛物线亚样本插值"的组合，期望把精度从 7 mm 降到亚毫米。经过 5 轮对照诊断发现：
- 抛物线插值对 **δ 冲激输入**只有 ~0.1 样本残差（符合理论）
- 但对 **chirp 匹配滤波输出**，由于 chirp 自相关主瓣非对称（线性调频导致相位-时间耦合），抛物线拟合产生 **~1 样本的算法本质偏置**（和理论预期差一个数量级）
- 用 16× 过采样生成的"真·延迟 0.25 样本 chirp"作为 ground truth 回归，偏置仍高达 +0.508 样本
- 故脚本最终回归"整数样本 argmax"的保守实现，所有数字 100% 可复现。亚毫米精度路径留给 D3 真机 POC，届时考虑 sinc 插值 / 复相关相位法 / 更高采样率

**第 3 层：双流 CNN（解决难点 #3）**

```python
left_input  = Input((20, 11))
right_input = Input((20, 11))

left_feat  = Conv1D(32,3)(left_input)  → Conv1D(64,3) → GlobalAvgPool  # (64,)
right_feat = Conv1D(32,3)(right_input) → Conv1D(64,3) → GlobalAvgPool  # (64,)

cross_feat = Concat([
    abs(left - right),         # 对称性
    left * right,              # 协同性
    distance_estimate          # 第 2 层算出的距离
])
cross_feat = Dense(32)(cross_feat)  # (32,)

merged = Concat([left_feat, right_feat, cross_feat])  # (160,)
output = Dense(50, 'softmax')(merged)
# 参数量/体积/延迟在 P4 训练后用 Edge Impulse "Model performance" 页实测填入；
# 单手 12K 参数 MVP 版在 ESP32-S3 上推理 ~15ms，双手版保守估计翻倍，仍在 50ms 预算内
```

- 左手流做**水平翻转增强**能白嫖 50% 训练数据
- Cross-stream 手工特征比纯学习稳（参考 MS-G3D、ST-GCN）

**第 4 层：端云分级（解决难点 #4）**
- 端侧先做 50 类闭集识别（具体延迟以训练后实测为准）
- 云端跑一个更大的 Transformer 扩大词表上限；模型规模、参数量、延迟、词表大小均为 P5 阶段建模决策，当前文档只锁定"分级调用"这一架构原则，不给数字
- 触发：端侧置信度低于阈值（阈值由验证集 ROC 曲线确定）时上传原始 22D × 窗口长度的特征流
- 降级：云端不可用回落端侧 top-1

**第 5 层：左右手差异化训练（解决难点 #5）**
- 采集：左右手各打同一手势 50 次
- 训练：左手数据额外做 [0.9, 1.1] 幅度增强
- 评估：分别算 left/right F1，差异 > 5% 回炉
